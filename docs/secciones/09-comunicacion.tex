\section{Modelo de comunicación entre servicios}

\subsection{Alcance y estado del diseño}

El equipo aceptó REST sobre HTTP con mensajes JSON y comunicación síncrona como mecanismo principal para la consulta académica mínima de E1.

Esta decisión se implementó mediante dos servicios independientes: el servicio de refuerzos, que inicia la consulta, y el servicio académico, que recibe la petición y devuelve la información solicitada.

La implementación permite comprobar la comunicación entre procesos y el tratamiento básico de errores, sin incorporar todavía las funcionalidades completas del SGRA.

La elección del mecanismo está documentada en ADR-002 y es coherente con la arquitectura propuesta en el modelo C4. Los servicios de E1 constituyen una demostración local y no representan el despliegue definitivo del sistema distribuido.

\subsection{Contrato de la consulta mínima implementada}
El \textbf{servicio de refuerzos} escucha en \texttt{127.0.0.1:8081} y expone la ruta \texttt{GET} \nolinkurl{/api/demo/asignaturas/{id}}. Al recibir una entrada válida, consulta al \textbf{servicio académico}, que escucha en \texttt{127.0.0.1:8082} y expone la ruta \texttt{GET} \nolinkurl{/api/asignaturas/{id}}.

El emisor devuelve al cliente el resultado de la consulta, sin utilizar una copia local de los datos académicos.

El catálogo utilizado es sintético y contiene únicamente la asignatura con identificador \texttt{1}. Para esta consulta, la respuesta correcta es HTTP \texttt{200}, con tipo de contenido \texttt{application/json} y el siguiente cuerpo:

\begin{verbatim}
{"id":1,"nombre":"Asignatura de demostración"}
\end{verbatim}

Un identificador no entero o no positivo produce HTTP \texttt{400}, con el código \texttt{ID\_INVALIDO}, sin consultar al receptor.

Un entero positivo distinto de \texttt{1} produce HTTP \texttt{404}, con el código \nolinkurl{ASIGNATURA_NO_ENCONTRADA}. El servicio de refuerzos conserva este resultado.

Cuando ocurre una desconexión, se agota un tiempo de espera, se recibe una respuesta HTTP \texttt{5xx} o el contenido del receptor es incompatible con el contrato esperado, el emisor está preparado para devolver HTTP \texttt{503}, con el código \texttt{SERVICIO\_ACADEMICO\_NO\_DISPONIBLE}.

Las pruebas manuales verificaron los estados HTTP \texttt{200}, \texttt{400} y \texttt{404}, así como el error \texttt{503} al detener el receptor y la recuperación posterior. El registro de integración recoge además ocho comprobaciones automatizadas con un receptor controlado, que incluyen respuestas incompatibles, un error HTTP \texttt{500}, el agotamiento del tiempo de lectura y la recuperación posterior. Estas comprobaciones se distinguen de las capturas de las pruebas manuales.

El mecanismo de comunicación REST/HTTP JSON fue aceptado por el equipo e implementado en la demostración E1. El cliente HTTP del servicio de refuerzos utiliza un tiempo de espera de conexión de un segundo y otro de lectura de un segundo, con una sola tentativa y sin reintentos automáticos.

Estos valores corresponden a la configuración implementada y no garantizan un tiempo máximo total de respuesta. No se realizaron mediciones de latencia de las operaciones completas del SGRA.

Para una implementación posterior se propone registrar el servicio, la ruta, el estado HTTP y la duración de cada operación.

La demostración utiliza memoria y datos sintéticos, sin base de datos, escrituras ni autenticación entre servicios. Ambos procesos escuchan exclusivamente en la interfaz local \texttt{127.0.0.1}.

La autenticación por sesión del navegador en el SGRA anterior se mantiene como contexto separado. Exponer los nuevos servicios fuera del equipo requerirá definir autenticación entre servicios y transporte protegido.

Las rutas implementadas corresponden a la demostración E1 y no sustituyen los endpoints del SGRA anterior.

\subsection{Justificación y evidencia experimental}

REST/HTTP con JSON se eligió para la consulta académica porque permite reutilizar las herramientas HTTP del equipo, mantener un contrato pequeño y comprobar las respuestas sin incorporar un intermediario de mensajes ni generar clientes. gRPC ofrece contratos Protocol Buffers y clientes generados; la mensajería permite diferir el procesamiento, pero una consulta con respuesta inmediata requiere además correlación y control de entregas. La elección considera esas necesidades y el esfuerzo de integración, además de las diferencias de rendimiento que puedan observarse en un ensayo concreto.

\paragraph{Condiciones de PE-U1.}
La práctica experimental comparó sockets TCP con JSON y gRPC con Protocol Buffers, mediante solicitudes y acuses entre tres procesos independientes en el mismo equipo~\cite{peu1-2026-resultados}. Se utilizó un AMD Ryzen 7 7730U, con ocho núcleos, dieciséis procesadores lógicos y aproximadamente 15,34 GiB de memoria física, Windows 11 y Python 3.13.15. El entorno gRPC empleó \texttt{grpcio} 1.76.0 y Protobuf 6.33.0. Las conexiones fueron persistentes y se establecieron antes de medir, sobre \texttt{localhost}, sin una red física entre equipos.

Se ensayaron cargas útiles de 100 y 10\,240 bytes de texto UTF-8, sin contar identificadores, serialización ni cabeceras. Para cada mecanismo, tamaño y modo se ejecutaron cinco repeticiones de 100 intercambios, después de una corrida de calentamiento excluida del análisis. En el modo concurrente, los tres emisores repartieron los cien intentos en 35, 35 y 30; esa carga no equivale a cien usuarios simultáneos. La comparación reúne 4\,000 intentos medidos en cuarenta corridas.

El tiempo de ida y vuelta (RTT) se midió en milisegundos desde la preparación y el envío hasta la validación y el registro del acuse, excluyendo la conexión inicial. El rendimiento se calculó como intercambios completados por segundo de duración del lote, incluida la coordinación local entre procesos. La Tabla~\ref{tab:peu1-comunicacion} presenta la media y el percentil 95 del RTT y la media del rendimiento. Los archivos originales conservan además la dispersión y los intervalos de confianza~\cite{peu1-2026-resultados}.

En estas condiciones, TCP/JSON registró un RTT medio menor y un rendimiento mayor que gRPC en los cuatro pares de tamaño y modo. No se registraron errores ni tiempos agotados entre los 4\,000 intentos medidos. Esto describe las implementaciones y el entorno de la práctica; no establece una superioridad general de TCP sobre gRPC ni una garantía de disponibilidad.

\paragraph{Aplicación al SGRA y límites.}
PE-U1 no ensayó REST/HTTP con JSON ni un intermediario de mensajes. Los sockets TCP con JSON no incluyen el protocolo HTTP, y los procesos Python de la práctica difieren de los servicios Spring Boot del SGRA. Tampoco se midieron consultas académicas de negocio, acceso a base de datos, autenticación, redes entre equipos ni conexiones nuevas por operación. Por tanto, estos resultados no permiten calcular la latencia de la consulta del SGRA ni afirmar que REST supere a gRPC.

La práctica aporta experiencia en contratos, serialización, medición y tratamiento de fallos. Para la consulta mínima se mantiene REST/HTTP con JSON por su adecuación al intercambio y su integración con la base existente. Una elección posterior deberá contrastarse mediante la misma operación de negocio, carga y entorno para cada alternativa. La configuración de tiempos de espera y las respuestas HTTP del esqueleto verifican comportamiento funcional; el rendimiento y la disponibilidad del SGRA requieren mediciones propias.

\subsection{Comprobación y cierre}
El esqueleto implementa ambos servicios con Spring Boot 4.0.10, Java 21 y Maven. Las pruebas de integración locales verificaron la consulta correcta (\texttt{200}), el ID inválido (\texttt{400}), la asignatura inexistente (\texttt{404}), el receptor detenido (\texttt{503}) y la recuperación posterior (\texttt{200}), sin reintentos automáticos. La reproducción técnica asistida desde un clon limpio está registrada en las evidencias de integración; queda por confirmar su reproducción por un segundo integrante. Los resultados de PE-U1 fundamentan la comparación con los límites descritos, y las pruebas del esqueleto respaldan la consulta HTTP implementada.
