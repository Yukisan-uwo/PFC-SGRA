\section{Modelo de comunicación entre servicios}
\subsection{Alcance y estado del diseño}
Se propone REST sobre HTTP con mensajes JSON y comunicación síncrona para una consulta académica mínima entre dos servicios de E1. ADR-002 conserva el estado \textbf{Propuesto}: faltan las mediciones originales de PE-U1, el C4 nivel 2 definitivo y la comprobación del esqueleto. En H3, \texttt{sendEmail} espera la operación SMTP y \texttt{sendEmailAsync} declara una delegación con \texttt{@Async}; su ejecución asíncrona efectiva depende de la configuración de Spring. Esto no acredita una cola durable ni un broker. En H5, el código conserva las validaciones Java si el proveedor no está configurado o falla. Las llamadas internas entre módulos Java no se cuentan como comunicaciones entre servicios desplegados independientemente.

\subsection{Contrato de la consulta mínima propuesta}
El \textbf{servicio de refuerzos} escuchará en \texttt{127.0.0.1:8081} y expondrá \texttt{GET /api/demo/asignaturas/\{id\}}. Al recibir una entrada válida consultará al \textbf{servicio académico}, que escuchará en \texttt{127.0.0.1:8082} y expondrá \texttt{GET /api/asignaturas/\{id\}}. El emisor devolverá el resultado al cliente; no resolverá la consulta con una copia local.

El catálogo será sintético y contendrá únicamente el entero positivo \texttt{1}. La respuesta correcta será HTTP \texttt{200}, con tipo \texttt{application/json} y el cuerpo siguiente:
\begin{quote}
\small\ttfamily
\{"id":1,"nombre":"Asignatura de demostración"\}
\end{quote}

Un ID no entero o no positivo producirá \texttt{400} con código \texttt{ID\_INVALIDO}, sin llamar al receptor. Un entero positivo distinto de \texttt{1} producirá \texttt{404} con código \texttt{ASIGNATURA\_NO\_ENCONTRADA}; refuerzos conservará este resultado. Una desconexión, espera agotada, respuesta \texttt{5xx} o respuesta incompatible del receptor producirá \texttt{503} con código \texttt{SERVICIO\_ACADEMICO\_NO\_DISPONIBLE}. Los errores tendrán un objeto JSON con la propiedad \texttt{codigo}, según ADR-002.

Se propone un presupuesto total de \textbf{dos segundos} para la llamada saliente, incluyendo conexión y lectura, con una sola tentativa y sin reintentos automáticos. Es una configuración inicial pendiente de medición, no un resultado experimental ni una garantía de duración de toda la petición. Se registrarán ruta, servicio, estado y duración para observar la comunicación.

La demostración usará memoria y datos sintéticos, sin base de datos, escrituras ni autenticación, y ambos procesos escucharán exclusivamente en loopback. La autenticación por sesión del navegador en el SGRA anterior se mantiene como contexto separado. Exponer los nuevos servicios fuera del equipo requerirá definir autenticación entre servicios y transporte protegido. Estas rutas son propuestas nuevas; no sustituyen las del sistema anterior.

\subsection{Justificación y evidencia pendiente}
REST/HTTP JSON permite usar las herramientas HTTP conocidas y comprobar el contrato sin un broker ni generación de clientes. gRPC permitiría un contrato Protocol Buffers y clientes generados, pero no hay una medición disponible que justifique introducir esas herramientas en este caso. Entre dos servicios backend gRPC no necesita una capa para navegador. La mensajería permite procesamiento diferido; para esta consulta exigiría correlacionar solicitud y respuesta y tratar entregas y duplicados. No se declara una ventaja de latencia o rendimiento de una alternativa sobre otra.

\subsection{Comprobación y cierre}
La implementación corresponde a los issues \#19 y \#33 y las evidencias de ejecución al \#34. Se deberá comprobar la consulta correcta (\texttt{200}), ID inválido (\texttt{400}), asignatura inexistente (\texttt{404}) y receptor detenido, lento o incompatible (\texttt{503}), verificando que no haya reintentos automáticos. Las pruebas todavía no se han ejecutado. El issue \#16 permanecerá abierto hasta incorporar PE-U1 y comprobar que C4, ADR-002 y llamada ejecutada describen la misma interacción.
